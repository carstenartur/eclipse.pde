# Current-source schema loading — 4 November 2026

## Findings

Coalescing avoids temporary DOM nodes and their later concatenation. It does
**not** reduce SAX `characters()` calls for identical input bytes and the same
parser. Formatting can reduce those calls by changing the input. Both mechanisms
are observed here, with identical resulting PDE schema models.

In the accepted four-block run, coalescing reduces benchmark-thread allocation
from 28.171 MB to 8.363 MB per full corpus load, and mean thread CPU from
18.070 ms to 13.953 ms. Compact formatting, applied on top of coalescing and
bounded parser reuse, reduces allocation further from 6.091 MB to 5.225 MB.
Its mean CPU is lower, but the descriptive interval includes zero savings.
That interval does not establish absence of a formatting effect.

These are warm full-model loads, not Eclipse startup timings. The separate
[GUI trace study](../trace-agent/RESULTS-GUI-2026-11-04.md) confirms actual XML
and, with restored schema editors, PDE schema loads during startup. It measures
attribution with heavy instrumentation, not patch speedup.

## SAX work versus DOM work

The following intrusive diagnostic is separate from timing. It covers the
49 top-level files only; the timed model operation also loads their includes.

| Input corpus | Bytes | SAX characters calls | Character units | Text nodes before normalization, baseline | Text nodes before normalization, coalesced |
| --- | ---: | ---: | ---: | ---: | ---: |
| Original | 617,841 | 29,100 | 395,124 | 29,100 | 9,473 |
| Current compact | 516,798 | 16,894 | 305,416 | 16,894 | 1,127 |
| Current indented | 552,273 | 25,238 | 340,744 | 25,238 | 9,471 |

Within each corpus, the baseline and coalesced handler have identical callback
counts, character units, normalized text-node counts and normalized DOM hashes.
The coalesced handler changes how it handles incoming chunks; the parser sends
the same chunks. Across different formatting corpora, whitespace and therefore
the literal DOM can differ. The PDE schema models remain equal, as separately
verified before timing. UTF-16 character units are not UTF-8 input bytes.

## Timing and allocation

The accepted series is `balanced-v2`: six cases in four blocks, with one fresh
JVM for every case and block, for **24 JVM observations**. Each JVM uses eight
two-second warmup iterations and six one-second measurement iterations. The
second block reverses the entire first-block case order; the next pair rotates
by one case and again uses an exact reverse. Every pair of cases therefore
appears in both relative orders.

The environment is Temurin 25.0.5+8, Linux, Serial GC, a fixed 512 MiB heap,
one benchmark thread and one active processor. Linux CPU affinity pins the JVM
to CPU 8 but does not reserve that CPU. The host is shared. CPU and allocation
are measured for the benchmark thread; GC/JIT/background-thread CPU and retained
heap are not measured by those counters.

| Implementation and input | Mean thread CPU, ms/load | Mean allocated MB/load |
| --- | ---: | ---: |
| Baseline, original | 18.070 | 28.171 |
| Coalescing, original | 13.953 | 8.363 |
| Reuse, original | 16.054 | 25.907 |
| Coalescing + reuse, original | 12.325 | 6.091 |
| Coalescing + reuse, compact | 10.440 | 5.225 |
| Coalescing + reuse, indented | 11.469 | 5.998 |

MB is decimal (1,000,000 bytes), not MiB. Means give every fresh JVM equal
weight. Six iterations within one JVM are not six independent forks. The
analysis uses the auxiliary counters' six `rawData` values, not their aggregate
JMH `score`, which is not the per-operation mean for this driver.

| Comparison | Mean CPU savings, ms/load | Descriptive 95% interval, ms | Mean allocation reduction |
| --- | ---: | ---: | ---: |
| Coalescing vs baseline | 4.117 | 1.268 to 6.967 | 70.31% |
| Reuse vs baseline | 2.016 | −0.431 to 4.463 | 8.04% |
| Combined vs baseline | 5.745 | 3.175 to 8.314 | 78.38% |
| Compact vs original, combined implementation | 1.886 | −1.039 to 4.811 | 14.23% |
| Indented vs original, combined implementation | 0.856 | −0.315 to 2.028 | 1.53% |

Positive savings mean the treatment took less CPU. Intervals use four paired
block differences and Student t with three degrees of freedom. They are
descriptive, are not adjusted for multiple comparisons and do not account for
uncertainty across machines, installations or workloads. Coalescing has positive
CPU savings in all four blocks here. The data do not justify a precise standalone
CPU percentage for reuse or formatting, and no row establishes an IDE startup
percentage. The consistent allocation differences and exact work counters remain
separate evidence.

## Preserved preliminary work

The earlier `originals` and `formatting` series have 12 and nine JVM observations.
Their cyclic rotation plus odd-block reversal accidentally left some treatment
pairs in the same order throughout. That was identified before the accepted
rerun. All raw results are retained, but their CPU means are excluded from the
headline comparison rather than selected according to outcome. Their counters
are not merged into the 24-observation accepted series.

The first `balanced` attempt stopped before measurement because the previous
JMH process still owned its lock. Its failure log is retained. The lock was
allowed to clear normally; no lock bypass or competing JMH run was used.
