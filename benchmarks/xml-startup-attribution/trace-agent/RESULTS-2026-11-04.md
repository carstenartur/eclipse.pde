# Local startup XML diagnostics — 2026-11-04

## Result

A real, recovered Eclipse product was run in three separate headless Equinox
JVMs, after the positive controls passed. A cold registry performs XML parsing
before the headless application starts. Reusing the registry cache removes those
registry manifest parses in this run, but does not remove the other SAX/XML work.
A later controlled automatic build exercises both Java and PDE builders and opens
the dependent plug-in's XML and the provider's schema.

All three final runs exited zero, passed the scenario assertions, produced a
successful probe result and ended with zero lost events, zero unfinished spans,
no trace/instrumentation errors and no Eclipse error log entries. The final
prepared restart did not report workspace recovery from unsaved changes.

The complete evidence is in [the run manifest](evidence/2026-11-04-headless/run-manifest.json),
[boundary comparison](evidence/2026-11-04-headless/boundary-comparison.json), and
[hash index](evidence/2026-11-04-headless/evidence-index.json). The raw JSONL traces
are retained as gzip without changing their uncompressed bytes. The hash index
records both compressed and uncompressed SHA-256 values.

## Before application entry

These values use the interval before `headless_application_entered`, not a GUI
readiness boundary. The automatic-build run uses a prepared registry and has the
same observed early XML counts as the prepared restart.

| Observation | Cold registry | Prepared restart |
| --- | ---: | ---: |
| Registry reports `loadedFromCache` | false | true |
| `ExtensionsParser.parseManifest` method entries | 170 | 0 |
| SAX parser method entries | 291 | 119 |
| Selected ZIP entry open attempts | 270 | 119 |
| XML ZIP bytes delivered before application entry | 2,219,945 | 63,447 |
| Job dispatch events before application entry | 8 | 0 |

The prepared run includes `OSGI-INF/*.xml` declarative-service descriptors; their
paths and callers are in the raw trace. This is direct evidence that the old
absence of PDE handler/schema counts before readiness was insufficient to claim
an absence of startup XML.

The byte values are uncompressed bytes delivered through observed ZIP-entry
streams. They are not physical disk reads, compressed JAR traffic or unique XML
bytes. Method counts can include nested overloads and repeated parses; counts
from different operation categories must not be added to obtain a document count.

## Automatic-build positive scenario

The fixture is a provider plus a dependent consumer, with JavaBuilder,
ManifestBuilder and SchemaBuilder on both projects. The provider declares its own
extension point and `.exsd`; the consumer contributes to that point and compiles a
class using the provider's exported Java package. The trigger enabled automatic
build and touched the provider's schema and consumer's `plugin.xml`. It did not
call an explicit full-build API.

During the trigger-to-completion interval, the final run observed:

- one actual `AUTO_BUILD` completion event;
- four PDE builder method calls and two Java builder method calls;
- four `Schema.load` entries, including nested overloads;
- seven observed opens of the consumer's `plugin.xml`, across the selected I/O
  layers/calls;
- zero build error markers.

The raw events preserve the project, build kind, source, caller, parent span,
thread and phase. Other XML work occurs after application entry as PDE models and
target registries initialize; it is not reclassified as the pre-application
interval in the table above.

## Controls and reproducibility

The final run passed eight JDK controls, five Eclipse controls, eight existing
probe logic checks and three real-descriptor checks. In particular, the real PDE
missing-JAR control records the failed resource open, keeps `Schema.isLoaded()`
false, and verifies that `Schema.load(InputStream)` is never entered. The direct
ZIP control records exactly 66 delivered bytes for its 66-byte XML payload.

The recovered installation contains PDE core

## Limits

This is actual headless Eclipse execution, not an actual workbench launch.
Although the GUI runner and PDE editor calls compile, the local machine lacks
Xvfb and the required X11 native library. The bounded GUI scenarios are ready for
the display-capable CI follow-up: cold registry, prepared restart, automatic
build during startup, editor seeding, and restoration on a separate restart.
Their coverage gates require separate ready/settled boundaries, EMF XML work,
build evidence and materialized editor observations. They have not been declared
successful in this local report.

The restored product configuration is not the original 243-resolved-bundle
primary timing environment. Its compiled PDE core matches the recovered
reference, but the product composition differs. The OS cache was uncontrolled and
expected to be warm. Heavy tracing affects execution and scheduling. The recorded
phase timestamps establish ordering and attribution; these runs do not measure
a patch speedup or establish a general cold-start latency difference.

The trace is limited to the instrumented classes and I/O methods documented in
[README](README.md). A final completeness flag means the selected event stream
completed without recorded loss; it is not proof of universal XML coverage.
